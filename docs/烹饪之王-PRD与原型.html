Product Requirements Document · v1.1

烹饪之王 · 家庭点菜微信小程序

组织化的烹饪管理，营造您自己的点餐—烹饪—出餐平台。产品模型不是"一个人向厨师下单"，而是每位成员独立点菜、汇总成制作任务、谁接单谁制作、逐道菜记录完成、统一确认出餐的协作系统。

形态 微信小程序 成员 家庭或小团队（共享数据） 数据范围 仅家庭内部 核心对象 餐次 · 个人点菜单 · 制作任务

01产品概述

已确认的产品决策在本版全部回填，不再以假设方式推进。

1.1 定位

面向家庭与小团队的私有饮食协作平台，以微信小程序为入口，覆盖饮食规划、个人点菜、接单制作、出餐确认、菜谱积累、饮食统计与营养分析。

1.2 已确认决策

决策项确认结果对设计的影响
使用平台微信小程序微信登录作为身份来源，微信订阅消息作为通知通道
账号模式家庭共享数据，区分成员身份数据以家庭为边界；"我"与"他人"必须可区分，权限校验在后端
点菜方式每人独立点菜，厨师汇总制作个人点菜单是独立对象，不能与汇总单合并成一张表
厨师安排谁接单谁制作不设固定厨师角色，改为"制作成员"按任务认领
通知方式微信通知优先站内通知为兜底基础通道，订阅消息为增强通道
菜谱录入手动录入，预留图片/文档 AI 导入菜谱表预留版本与导入任务结构，第一版不实现解析
点菜截止成员手动确认汇总并开始制作不做定时截止任务，避免时区与超时状态复杂度
份数含义默认每人点自己的份数，可标记多人共享份数 ≠ 食用人数 ≠ 实际摄入量，三者分开记录
出餐确认厨师确认出餐，允许逐道菜记录完成菜品状态与整餐状态分离，两层状态机
营养录入第一版接入 AI 估算 + 人工确认营养估算有独立状态：待估算 → 待确认 → 已确认
存储方式先设计可替换架构业务接口稳定，底层存储与三方服务通过适配层隔离
确认菜单权限仅家庭创建者可点「确认并开始制作」确认是唯一的"锁定点菜、生成任务"入口，权限收敛到一人
追加菜品确认后不开放追加想补菜走「加餐」，不做追加窗口与变更流程
加餐次数不限次数，一天可多个加餐餐次唯一约束不能只按 日期+餐次类型，需引入序号
成员在家状态不做不维护"是否回家吃饭"，提交进度只反映点菜动作
期望用餐时间不做不设置开饭时间点，厨师按接单顺序处理
忌口与过敏作为成员档案结构化维护点菜时对命中过敏原的菜提示，制作时高亮
食材采购清单由餐次汇总自动生成按总份数换算食材用量并按食材合并
菜谱归档归档后不进入点菜候选与随机抽菜，可恢复支持「不再常做」与「时令菜过季」两种场景
成员退出历史点菜与出餐记录保留在家庭不随成员退出而删除或匿名化

1.3 目标与边界

目标衡量方式
降低选菜成本支持搜索、标签筛选、随机推荐，从打开到提交点菜单不超过一次连续操作
提高协作效率多人点菜后可在汇总页看到合计份数与每个人需求
沉淀家庭菜谱资产菜谱可创建、修改、归档，历史订单引用不受删除影响
保证过程可追踪从个人提交到实际出餐每一步都有状态、责任人与时间
了解饮食规律可查看历史菜单、热门菜、餐次分布与营养趋势

不做：公开菜谱社区、外卖与支付、商家管理、库存采购、多人跨家庭共享。第一版一个微信用户只加入一个家庭。

02业务流程与对象模型

先说清楚"哪些东西是不同的东西"，这是本产品最容易设计错的地方。

2.1 主流程

创建家庭 / 邀请成员→ 维护菜谱→ 各成员选日期餐次→ 提交个人点菜单→ 汇总为制作任务→ 接单制作→ 逐菜完成→ 确认出餐→ 归档与统计

2.2 四个不能合并的对象

对象定义为什么不能合并
家庭成员、菜谱、餐次、任务、通知、统计的共享边界是所有数据的隔离单位，权限与统计都挂在它上面
餐次某一天的早 / 中 / 晚 / 加餐是时间容器；把"订单"当中心对象会让多餐多任务无处归属
个人点菜单每位成员在某个餐次里的独立选择合并后无法还原"谁的几份"，个人营养与改单都会失真
制作任务汇总后由接单人负责的执行单元，内含多个菜品明细制作由"谁接单"决定，与点菜人无关
关键例子
三个成员在同一顿晚餐都点了番茄炒蛋：A 点 1 份、B 点 1 份、C 点 2 份。系统汇总成"番茄炒蛋 4 份"的制作任务，但必须保留 4 份需求分别来自谁 —— 否则既算不出个人摄入，也无法在有人改单时准确扣减。

2.3 对象链路

层级对象基数关系
1家庭 Household1 : N 成员 / 菜谱 / 餐次
2餐次 Meal Session1 : N 个人点菜单；1 : 1 汇总单
3个人点菜单 Personal Order1 : N 菜品明细；每餐每人仅一份有效单
4餐次汇总单 Meal Aggregate1 : N 制作任务；保存汇总快照
5制作任务 Production Task1 : N 菜品明细；任一时刻至多一个有效接单人
6出餐记录 Serving Record记录计划份数与实际份数
7营养摄入 Nutrition Intake按成员 × 餐次记录实际食用份额与营养素

03角色与权限

不设复杂管理员体系；角色可叠加，家庭创建者也能点菜和接单。

3.1 角色定义

角色权限叠加
家庭创建者创建家庭、邀请成员、管理成员与家庭设置、转移创建者；唯一有权确认菜单并开始制作可叠加其余全部
普通成员浏览菜谱、独立点菜、修改本人未锁定点菜单、查看家庭菜单与统计基础角色
制作成员认领待接任务、开始制作、更新进度、登记逐菜完成、确认出餐由"接单"动作获得，不预先任命
菜谱贡献者创建菜谱、编辑自己创建的菜谱是否可改他人菜谱由家庭设置决定 待定

3.2 身份与隔离

  • 微信登录换取服务端会话，服务端解析身份，不信任客户端传入的 userId。
  • 每个家庭一个独立数据空间，成员通过邀请码/分享卡片加入。
  • 邀请码有有效期与使用次数上限，避免私有数据被无关人员访问。
  • 第一版一个微信用户只加入一个家庭；多家庭切换列为后续。
  • 创建者退出前必须能转移权限，不能让家庭空间失去管理能力。

06UI 原型

干净、白底、少色、强留白：只用一种强调色承担主操作，状态色仅在必要时出现。

07关键页面交互要求

只写会影响开发判断的规则，不重复 UI 通用规范。

全局

  • 主按钮固定在底部安全区，不遮挡内容；所有提交显示加载态，防连点重复请求。
  • 网络失败保留已填写草稿；返回时恢复未提交的选择。
  • 同一状态在不同页面必须使用同一名称与颜色。
  • 删除、撤销、取消、确认出餐等操作需二次确认。
  • 空页面必须给出下一步动作，例如"还没有菜谱，创建第一道菜"。

首页（P03）

  • 顺序：日期与成员 → 四个餐次状态卡 → 待处理事项 → 快捷操作 → 最近出餐。
  • 优先突出"现在该做什么"，不把统计图表塞进首页。
  • 未提交的成员按"进度"表达，不标记为异常或错误。

点菜（P07 / P08）

  • 卡片主体进详情，数量控件只负责加减份数，互不干扰。
  • 清单与菜谱列表共享同一份页面状态，来回切换不丢选择。
  • 份数为非负整数，至少一道菜且份数 ≥ 1 才能提交。
  • 支持"多人共享"标记，并填写预期共享人数或总制作份数。
  • 切换日期或餐次时提示是否保存当前草稿。
  • 若服务端返回已锁定，前端重新拉取状态，并保留未提交的变更供查看。
  • 勾选命中本人过敏原的菜品时，卡片上给出提示但不阻断；提示文案随菜品变化，不弹全局弹窗。

汇总（P10）

  • 必须同时表达三件事：谁点了什么、总共要做多少、哪些要求不能合并。
  • 「确认菜单并开始制作」是一个业务事务，不是两个前端请求；按钮仅对家庭创建者可见可用，其他成员看到的是"等待创建者确认"。
  • 口味冲突时给出提示，由厨师选择分锅或统一制作后分配，不静默丢备注。
  • 确认后页面不再出现"添加菜品"入口；如需补菜，引导至"新建加餐"。

制作（P16 / P17 / P18）

  • 制作详情优先展示菜名、总份数、食材与步骤；成员需求、备注、营养放次级区域。
  • 接单按钮文案明确责任：「接单并负责制作」。
  • 每完成一道菜即时打勾并显示已完成 / 剩余；全部必需菜品完成后才开放出餐确认。
  • 确认出餐后禁止普通用户直接改历史记录；数量纠错走带原因的修正流程并留审计。

菜谱（P12 / P13）

  • 信息层次：图与名 → 标签 → 时长/难度/适用餐次 → 营养摘要 → 食材 → 步骤 → 成员备注。
  • 食材用量与默认份数关联，调整份数时展示按比例换算的参考用量。
  • 两人同时编辑同一菜谱时使用版本号/ETag，后提交者不得静默覆盖。
  • 菜谱列表默认只显示「可用」，提供「已归档」入口查看与恢复；归档不提供删除，避免历史订单出现空引用。

统计（P19 / P20）

  • 家庭视角与个人视角分开，不混为一谈。
  • 每个图表标注时间范围、单位与口径（按提交次数还是按出餐次数）。
  • 点了两份不代表全由本人吃掉；出餐了也不代表每位成员都吃了。

08业务规则与状态机

界面可以迭代，但状态与并发规则一旦设计错，返工成本最高。本节是全系统唯一定义。

8.1 餐次状态

状态进入条件允许的操作
未开始尚未开放点菜或无任何点菜活动发起点菜
点菜中允许成员提交、修改个人点菜单提交 / 修改 / 撤销本人点菜单
待制作汇总确认后进入制作阶段，点菜单锁定认领制作任务
制作中至少一个制作任务已开始逐菜完成、登记异常
部分出餐部分菜品已完成出餐，仍有必需任务未完成继续制作、部分确认
已出餐全部必需任务完成并确认出餐只读回看
已取消整个餐次取消只读回看，不计入统计

加餐不限次数：早餐、午餐、晚餐各一天一个；加餐可创建多个（如下午茶 + 夜宵），每个加餐是独立餐次，各自点菜、汇总、制作、出餐，互不影响。

餐次状态与制作任务状态分开维护；页面不自行推导状态，必须读取服务端返回的餐次状态。

8.2 个人点菜单状态

状态可修改人说明
草稿仅本人未提交，可自由增删
已提交仅本人已进入家庭汇总，可继续修改
已锁定无人可直接改制作阶段开始后锁定，需走变更流程
已完成归档—餐次结束，保留历史快照
已取消本人（锁定前）不计入有效订单与统计

A 在其他成员已提交后修改自己的菜单时，只重算汇总，不得改动其他人的点菜单。

8.3 制作任务状态

状态进入条件约束
待接单汇总确认后生成家庭成员均可认领；并发下仅一个成功
已接单认领成功接单人为负责人；可开始制作
制作中负责人点开始制作他人不可直接接管，除非显式转交
已完成全部必需菜品完成不可由普通操作改回制作中
异常（取消 / 失败 / 部分完成）登记异常必须记录原因、处理人、时间

「谁接单谁制作」的含义是：接单人是该任务的负责人，其他人仍可协助，但第一版只需保证负责人明确。

  • 规格或口味要求不一致时，拆成不同制作明细，或明确提示厨师。
  • 总份数必须等于有效个人需求之和。

8.5 点菜截止与制作开始

  • 采用手动确认汇总：由成员确认需求已齐后点「确认菜单并开始制作」，不做定时截止。
  • 仅家庭创建者有权执行确认。普通成员只能提交与修改自己的点菜单。
  • 确认后锁定相关点菜单并生成制作任务；不开放追加。想补菜请新建一个「加餐」餐次，走完整点菜流程。
  • 确认前若存在口味冲突，页面提示但不阻断确认，由创建者判断是否先沟通。
需要注意的单点风险
确认权限收敛到创建者后，创建者不在线时餐次会停在「点菜中」无法进入制作。缓解方式有两个，可后续择一：创建者把权限转移给在家的成员，或增加「创建者可预先授权某人代确认」。当前版本按"仅创建者"执行。

8.6 营养与实际摄入

营养统计用三层数据：菜谱营养估算 → 实际出餐份数 → 个人实际食用份额。

估算 300 kcal/份的菜做了 4 份，成员 A 只吃了 0.5 份 → A 的估算摄入是 150 kcal，而不是 300 或 1200。
  • 第一版以"点菜份数"作为个人摄入份额参考，界面标注「按点菜份数估算」。
  • 后续增加「调整实际食用量」后，再升级为更贴近真实的摄入记录。
  • 营养值一律为估值，不做医学级承诺；AI 估算必须经人工确认后才参与统计。

8.7 菜谱归档与「时令菜」

归档是什么：归档 = 把菜谱停用但不删除。数据完整保留，历史点菜、出餐记录与统计中的引用都不受影响，随时可以一键恢复为可用。它替代了"直接删除"，避免历史数据出现空洞。

状态含义是否进入点菜候选 / 随机抽菜
可用 active正常在库，可被点选是
已归档 archived停用但保留，可在「已归档」列表查看与恢复否
时令 seasonal（P1）设置了供应月份区间，非供应期自动按归档处理仅在供应月份内

两个典型场景：

  • 不再常做：某道菜吃腻了或季节不合适，先归档，看不见但不丢；哪天想吃了再恢复。
  • 时令菜（你举的例子，完全成立）：春天的香椿炒蛋、夏天的凉面。春季恢复上架可点，夏天到了归档停售，菜谱仍然存着，明年春天从归档里取出来继续用。这就是归档最实用的价值。

如果希望"到季节自动上架、过季自动下架"，在菜谱上维护供应月份区间即可（REC-11，P1）；在此之前用手动归档/恢复也完全够用。

归档不影响历史：已归档菜谱仍会出现在旧订单的菜品快照中，统计照常计入历史出餐记录。

  • 提示不阻断点菜：由本人决定是否仍要这道菜，系统只负责让人知情。
  • 汇总页与制作任务详情高亮全部成员的禁忌，避免厨师误放。
  • 命中依赖菜谱食材已结构化；食材名做同义词映射（如"牛里脊 / 牛肉"）。映射不到时宁可不提示，也不误报。
  • 仅作家庭内提醒，不构成医学建议；不提供给第三方。

8.9 食材采购清单

  • 生成时机：创建者确认菜单、生成汇总时一并生成，挂在餐次下，之后随时可查看。
  • 换算公式：食材用量 = 菜谱基准用量 ÷ 基准份数 × 该菜总份数。
  • 合并规则：同名且同单位的食材相加；单位不同（如"1 颗"与"200 g"）不强行合并，分行列出。
  • 精度：可数项向上取整到可购买单位（1.5 个 → 2 个）；重量保留到 10 g。
  • 勾选已备只改变清单状态，不回写汇总份数，也不影响已生成的制作任务。
  • 清单基于汇总快照生成，菜谱后续修改不影响本餐已生成的清单。

10共享规则

跨模块复用的唯一定义，功能章节只引用。

10.1 通知

事件接收人通道
制作任务生成全体家庭成员站内通知（P0）+ 微信订阅消息（P1）
任务被认领其他家庭成员站内通知
单道菜完成该菜的点选人站内通知（可合并，不逐道推送）
确认出餐全体家庭成员站内通知 + 微信订阅消息
餐次被取消 / 菜品异常相关成员站内通知

通知不得在业务事务内直接调用微信接口：先在事务中写入待发事件，提交成功后再由后台任务投递，失败可重试。

关于"登录时授权一次、此后无需再次授权"，技术上做不到
已核实的微信小程序规则：一次性订阅是"授权一次只能下发一条"，用户勾选「总是保持以上选择，不再询问」只是下次调用时不再弹窗，并不等于永久免授权——每次调用仍只增加 1 条下发额度；且同一用户在同一 scene 场景值下的多次授权不累积，需要多条必须使用不同 scene 值。长期订阅（授权一次可长期下发多条）只开放给特定线下公共服务类目，家庭工具申请不到。旧的模板消息能力也已不再对小程序开放。

因此通知按以下四层落地：

  1. 站内通知为必达基础通道（P0）：通知中心列表 + 首页待处理角标，完全不依赖用户授权，任何事件都先保证有一条站内记录。
  2. 登录时请求订阅授权：首次进入时一次性申请「新任务」「已接单」「已出餐」等模板，并用「总是保持以上选择」把后续打扰降到最低——用户侧表现为"以后不再弹窗"。
  3. 关键动作处静默累积额度：在提交点菜、确认菜单、接单、开始制作、确认出餐等动作后顺带调用订阅接口，每次 +1 条额度。用户不会看到额外弹窗，但额度会被持续补充。
  4. 额度记账与降级：记录每种模板的剩余可下发条数；额度不足时自动降级为站内通知，并在页面提示"开启提醒可收到微信通知"，绝不假装已发送。

可选增强：用户主动与小程序客服会话后 48 小时内可用客服消息补发（P1，需用户先发起会话）。

10.2 快照与版本

  • 点菜明细保存菜谱快照（名称、份量、营养、食材、步骤），菜谱后续修改或归档不影响历史。
  • 汇总单保存汇总快照，制作任务保存规格快照，出餐记录保存实际数量。
  • 菜谱、个人点菜单、制作任务均带 version，写操作校验版本，冲突时返回冲突让前端刷新。
  • 接单时间、出餐时间、审计时间一律由服务端生成。

10.3 并发控制

场景手段失败表现
认领任务条件更新（status=pending 且 assignee 为空）受影响行数为 0 → 返回"已被他人接单"
编辑菜谱version / ETag 比对返回冲突，提示刷新，不静默覆盖
保存点菜单version 比对 + 餐次状态校验返回冲突或"已锁定"
确认菜单单事务（校验→锁单→汇总→建任务→事件）任一步失败整体回滚，不留半完成状态

10.4 存储与外部服务可替换边界

  • 业务模块只依赖 Repository 接口，不依赖具体 ORM 或数据库方言。
  • 文件存储走 S3 兼容适配器，上传用受控临时凭证（presign），不把小程序的长期密钥放在前端。
  • AI 营养估算走独立 NutritionProvider 接口，可替换模型或服务商。
  • 微信通知走订阅消息适配器，站内通知始终保留为基础通道。
  • 可替换 ≠ 零成本：换库涉及方言、隔离级别、索引与数据迁移；换存储涉及上传授权与访问控制，需单独评估。

11.4 安全要求

  • 公网服务器只开放 443 与 SSH（SSH 限密钥、可限 IP），frps 其余端口不对外。
  • API 全量鉴权：服务端解析微信会话并校验家庭成员关系，不信任客户端传入的任何身份参数。
  • 图片访问使用带签名的临时 URL，对象存储桶不开放公开读。
  • Nginx 开启基础限流，防止被刷。
  • 日志不记录 openid 明文、手机号等敏感字段；家庭主机磁盘加密。
