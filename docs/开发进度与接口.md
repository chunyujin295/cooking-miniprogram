# 烹饪之王 · 开发进度与接口

> 更新时间：2026-10-27（里程碑 M1）。与实际部署一致；产品需求与原型见 [烹饪之王-PRD与原型.html](./烹饪之王-PRD与原型.html)。

## 0. 里程碑 M1（2026-10-27）

**范围**：阶段 0–3 全链路闭环 + 统计/随机抽菜 + 昵称/头像 + 站内通知与订阅消息模板。

**已验收的关键链路**（服务器真实环境实测）
1. 微信登录 → 建家庭 → 生成邀请码
2. 菜谱：新建（多图）→ 列表/筛选 → 详情 → 编辑 → 归档/恢复
3. 点菜：餐次/加餐多实例 → 选菜调份数 → 提交 → 汇总（各人明细 + 合计需求）→ 创建者确认生成制作任务
4. 制作：认领 → 开始制作 → 逐菜完成 → 确认出餐（落出餐记录、餐次置 served）
5. 统计：已点菜份数 / 已出餐份数 / 餐次分布 / 热门菜 / 随机抽菜（排除归档、过季、近期）
6. 通知：菜单确认 / 接单 / 出餐三条站内通知；订阅消息三张模板接通（真机需授权）
7. 营养：菜谱详情展示每份热量（随模板导入）→ 人工确认 → 统计页按出餐份数汇总
8. 菜谱整理：复制提示词到外部 AI 整理 → 粘贴 JSON → 核对保存（不调用小程序内模型）

**部分待补**：营养目前只支持「模板带入 + 人工确认」，暂不支持手动改数值与个人摄入明细（`nutrition_intakes` 表未启用）。

### 餐次与点菜

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/meal-sessions?date=YYYY-MM-DD` | 当天所有餐次 |
| GET | `/meal-sessions/calendar?month=YYYY-MM` | 月历：按日返回餐次状态与是否有提交/出餐 |
| POST | `/meal-sessions` | 取或建餐次；加餐 seq 自动递增 |
| GET | `/meal-sessions/:id` | 详情：我的单、全员明细、汇总需求、canEdit/canConfirm |
| DELETE | `/meal-sessions/:id` | 删除空餐次（无人提交、未确认）；别人已提交时仅创建者可删 |
| PUT | `/meal-sessions/:id/orders/mine` | 保存草稿 |
| POST | `/meal-sessions/:id/orders/mine/submit` | 提交 |
| POST | `/meal-sessions/:id/confirm` | 仅 owner；生成汇总单 + 制作任务并锁定点菜单 |

说明：`POST /meal-sessions` 对加餐会**复用最近一个空加餐**，避免重复点击产生多条空餐次。

状态机：`not_started → ordering →（确认）pending_production →（接单）producing →（出餐）served`；点菜单 `draft → submitted → locked`。

### 营养与热量

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/recipes/:id/nutrition` | 该菜每份营养；未录入返回 `null` |
| POST | `/recipes/:id/nutrition` | **主路径**：保存外部 AI 模板给出的每份营养，`source=external-ai`、`isConfirmed=false` |
| POST | `/recipes/:id/nutrition/confirm` | 人工核对后确认，才视为可信数据 |
| POST | `/recipes/:id/nutrition/estimate` | 内置模型估算，**保留备用**；小程序已不暴露入口，需要 LLM Key |

口径：所有数值都是**每 1 份**（对应菜谱 `baseServings` 换算后）；统计页按「出餐份数 × 每份能量」估算，未录入的菜不参与汇总，界面会显示覆盖率。

### 菜谱整理（模板导入）

小程序不调用大模型，流程是「复制提示词 → 用户在自己的 AI 里整理 → 粘贴 JSON 回小程序」。服务端只有这次改造之前的接口，保留但不作为主路径：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/recipe-imports` | 旧的「链接/文字识别」接口，保留备用（需 LLM Key、有配额与熔断） |
| GET | `/recipe-imports/:id` | 旧导入记录，排查用 |
| POST | `/recipe-imports/:id/link` | 旧接口，回填 `recipeId` |

模板导入的实现要点：
- 提示词是客户端常量 `constants/recipePrompt.ts`，内含 `schemaVersion`、字段约束和示例；`utils/recipeDraft.ts` 负责容错解析（允许 ```json 包裹、允许前后解释），并按字段缺失给出可读错误。
- 解析成功后只预填编辑页，**用户核对并保存**才入库；保存时带上 `source=external-ai`，详情页显示「外部整理」标记。
- 营养值随模板一起带（`nutritionPerServing`），保存菜谱后写入 `recipe_nutrition`，仍需人工「确认数据」。
- 旧的内置 AI 与链接抓取代码（`infra/llm`、`recipe-import`）**未删除**，服务器上接口仍然可用，只是客户端不再调用；`LLM_API_KEY` 可保留也可清空。

合规说明：生成行为发生在用户自己的 AI 工具里，小程序只做结构校验与展示，因此不构成「向公众提供生成式 AI 服务」；公开发布时仍需注意文案中性、预览页标注来源、按需接 `msgSecCheck`。

| 方法 | 路径 | 说明 |

| POST | `/production/tasks/:id/accept` | 接单（条件更新，防并发重复接单） |

### 采购清单

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/shopping-lists/by-session/:sessionId` | 取该餐采购清单；不存在时按「已提交/已锁定」点菜即时生成（幂等，重复调用返回同一份） |
| POST | `/shopping-lists/items/:itemId/toggle` | 勾选 / 取消「已备」 |

生成规则：每道菜按 `点菜份数 ÷ 菜谱 baseServings` 缩放食材用量，同名同单位食材合并（不同单位不合并）；用量解析不到数字（如「适量」）时保留文案原样。清单挂在餐次上，入口在汇总页与制作页。

### 统计与通知

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/stats/overview?days=7\|30` | 出餐餐次 / 菜品次数 / 总份数 / 热门菜 / 餐次分布 |
| GET | `/stats/random?count=&excludeDays=&tagIds=` | 随机抽菜：排除归档、过季时令、近 N 天已吃 |
| GET | `/notifications` | 我的通知（未读数 + 最近 50 条） |
| GET | `/notifications/unread-count` | 未读数 |
| POST | `/notifications/read-all`、`/notifications/:id/read` | 标记已读 |
| GET | `/notifications/config` | 订阅消息模板 id（未配置返回空数组） |

通知触发点：菜单确认、任务接单、整餐出餐。写入 `notifications` 表；模板未配置时状态为 `skipped`，不会标记成已发送。

## 6. 订阅消息模板对照

| 业务事件 | 模板 | 编号 | 字段映射 |
| --- | --- | --- | --- |
| 菜单确认（`meal_confirmed`） | 新订单通知 | 2917 | `phrase1`=餐次、`thing8`=共 N 份任务已生成、`date4`=确认日期 |
| 有人接单（`task_accepted`） | 服务人员接单通知 | 33346 | `thing2`=餐次、`thing3`=接单人昵称、`time5`=接单时间 |
| 整餐出餐（`meal_served`） | 订单完成通知 | 12621 | `thing12`=餐次、`thing16`=共 N 份已出餐、`time5`=出餐时间 |

约束：`phrase` 最多 5 个汉字、`thing` 最多 20 个汉字，代码里已按上限截断。`page` 统一跳 `/pages/notification/index`。

模板未配置、用户未授权（43101）或 openid 无效时，`notifications.status` 记为 `failed`/`skipped`，站内通知仍可正常查看，不会误标为已发送。

## 7. 已知缺口与待办

1. **阶段 4 营养估算**：已上线 AI 估算 + 确认 + 统计汇总；剩余「人工手改数值」「`nutrition_intakes` 个人摄入明细」未做。
